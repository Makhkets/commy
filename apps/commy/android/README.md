## Что здесь делается и чего здесь не делается

Ровно четыре обязанности, по [`docs/02-architecture.md`](../../../docs/02-architecture.md):

1. получить дескриптор TUN,
2. реализовать `PlatformInterface`,
3. управлять жизненным циклом сервиса,
4. показать системный UI (уведомление, тайл, системный диалог VPN).

Всё остальное — Dart. Если в этой папке появился разбор подписки, сборка
конфига, выбор приложений для раздельного туннелирования или расчёт маршрутов —
это ошибка слоя, а не оптимизация. Маршруты и списки пакетов приходят **уже
посчитанными** в `TunOptions`; Kotlin только перекладывает их в
`VpnService.Builder`.

Ещё одно следствие того же правила: **нативная сторона не может сама поднять
туннель.** Для этого нужен сгенерированный конфиг, а он несёт все креды
пользователя и по правилу R2 лежит в зашифрованном хранилище на стороне Dart.
Поэтому и тайл, и загрузка устройства умеют только одно — попросить пользователя
открыть приложение.

## Три вещи, которые все восстанавливают по памяти неправильно

Проверено по `javap` на том самом AAR, который лежит в `app/libs/`.

1. **`NewService` не существует.** Туннель поднимается так:

   ```kotlin
   Libbox.setup(SetupOptions)                      // один раз за процесс
   val server = Libbox.newCommandServer(handler, platformInterface)
   server.start()
   server.startOrReloadService(configJson, null)   // ← туннель встаёт здесь
   ```

   `startOrReloadService` изнутри зовёт `PlatformInterface.openTun()`, и вот там
   уже собирается `VpnService.Builder`.

2. **У `PlatformInterface` ровно 15 методов.** `packageNameByUid`, `writeLog` и
   `usePlatformDefaultInterfaceMonitor` **не существуют** — их добавляют по
   памяти. Лишний метод ломает сборку на линковке, а не в рантайме.

3. **Смена сети — это не пересоздание TUN.** Это
   `InterfaceUpdateListener.updateDefaultInterface(...)` плюс
   `CommandServer.resetNetwork()`. Doze — это `pause()` / `wake()`. Ни то, ни
   другое туннель не рвёт.

Ещё две мелочи, на которых теряется время:

- у `RoutePrefix` методы **без** `get`: `address()`, `prefix()`, `mask()`;
- Kotlin не делает свойство из геттера, чьё имя продолжается заглавными:
  `item.getURLTestDelay()`, `event.getID()`, `options.getMTU()` — только вызовом.

## Сборка

Ядро уже собрано и лежит в `app/libs/libbox.aar` (14 МБ, `arm64-v8a`).
Пересобирать его Gradle **не умеет и не должен**:

```bash
scripts/build_core.sh android          # → core/build/libbox.aar
```

Если файла нет, `preBuild` падает с внятным текстом и ссылкой на скрипт, а не с
`unresolved reference: io.nekohasekai` из глубины компилятора Kotlin.

```bash
cd apps/commy
fvm flutter run -d <device>            # отладочная сборка
fvm flutter build apk --release        # → build/app/outputs/flutter-apk/
```

ABI splits включены: `arm64-v8a`, `armeabi-v7a`, `x86_64` плюс universal APK.
32-битный ARM оставлен намеренно — в регионах, ради которых это приложение
существует, полно дешёвых телефонов, никогда не видевших arm64-сборки.

### Подпись

Релизная подпись **необязательна**. Без ключа сборка всё равно даёт
устанавливаемый APK, подписанный debug-ключом, — на этот откат опирается CI, и
проект, который не собирается, пока кто-то не выложит keystore, — это проект,
в который нельзя контрибьютить.

`android/key.properties` (в `.gitignore`):

```properties
storeFile=/absolute/path/commy.jks
storePassword=…
keyAlias=commy
keyPassword=…
```

Либо переменные окружения — их читает CI:
`ANDROID_KEYSTORE_PATH`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`,
`ANDROID_KEY_PASSWORD`.

## Разрешения: что просим и чего не просим

| Разрешение | Зачем |
|---|---|
| `INTERNET`, `ACCESS_NETWORK_STATE` | сеть и отслеживание сети по умолчанию |
| `FOREGROUND_SERVICE` + `..._SYSTEM_EXEMPTED` | туннель живёт в foreground-сервисе |
| `POST_NOTIFICATIONS` | Android 13+; отказ переживаем — туннель работает, просто молча |
| `RECEIVE_BOOT_COMPLETED` | только когда включён автозапуск |
| `CAMERA` | импорт по QR, спрашивается в момент открытия сканера |

**Чего сознательно нет, хотя референсный клиент просит:**

- **`QUERY_ALL_PACKAGES`.** Вместо него блок `<queries>` с
  `MAIN`/`LAUNCHER` — он даёт ровно те приложения, которые пользователь видит в
  лаунчере, а это и есть то, что нужно пикеру раздельного туннелирования.
  Широкое разрешение дополнительно раскрыло бы скрытые пакеты и требует
  обоснования в Play. Возможность прочитать полный список приложений
  пользователя приватного инструмента — не та возможность, которую мы хотим
  иметь.
- **`ACCESS_FINE_LOCATION` / `ACCESS_COARSE_LOCATION`.** На Android именно они
  открывают SSID, который libbox спрашивает через `readWIFIState()`. Возвращаем
  `null`. Цена: правила маршрутизации по имени Wi-Fi сети не сработают.
  Развернуть это назад — значит поменять модель угроз, а это пункт 4 из §7
  `CLAUDE.md`, то есть решение владельца.

### `foregroundServiceType`

`systemExempted`. Android 14 сделал тип обязательным и не завёл типа для VPN;
`systemExempted` — то, что отдаёт референсный клиент sing-box и что платформа
выдаёт приложению, держащему VPN-слот. `specialUse` объявлен вторым и
пробуется, если платформа отказала в первом: `ForegroundServiceTypeNotAllowedException`
— это туннель, который не стартует, на устройстве, которого у нас нет.

## Ручной чек-лист M1

Автотестами это не закрывается: нужен реальный APK на реальном устройстве и
реальный сервер. Первые четыре пункта — **критерии приёмки M1** из
[`docs/07-roadmap.md`](../../../docs/07-roadmap.md), а не пожелания.

### 1. Трафик реально идёт

- [ ] импортировать `vless://` со своего сервера, подключиться;
- [ ] `whoami`-сервис показывает IP сервера, а не провайдера;
- [ ] IPv6-проверка не показывает домашний адрес (утечка мимо туннеля);
- [ ] DNS-проверка не показывает резолвер провайдера;
- [ ] в уведомлении растут цифры скорости, на графике в приложении — тоже.

### 2. Туннель переживает смену сети

Ключевое: **соединения не рвутся, TUN не пересоздаётся.**

- [ ] на Wi-Fi запустить долгую загрузку;
- [ ] выключить Wi-Fi — телефон уходит в мобильную сеть;
- [ ] загрузка продолжается, переподключаться руками не надо;
- [ ] состояние в приложении не уходило в `error`;
- [ ] обратно на Wi-Fi — то же самое;
- [ ] режим полёта на 10 секунд и обратно — туннель восстанавливается сам;
- [ ] в `logcat -s CommyNetwork` видно смену интерфейса, а **не** перезапуск.

### 3. Туннель переживает сон и Doze

- [ ] `adb shell dumpsys deviceidle force-idle`;
- [ ] подождать, разбудить: `adb shell dumpsys deviceidle unforce`;
- [ ] туннель по-прежнему поднят, трафик идёт;
- [ ] в `logcat -s CommyDoze` видно `pause` и `wake`, а не рестарт сервиса;
- [ ] то же вживую: заблокировать экран на 30+ минут, потом открыть.

### 4. Отказ в системном диалоге VPN даёт понятную ошибку

Тишина здесь — это именно тот баг, ради которого критерий записан.

- [ ] отозвать разрешение: Настройки → Сеть → VPN → Commy → удалить;
- [ ] нажать «Подключиться», в системном диалоге нажать «Отмена»;
- [ ] приложение показывает понятную ошибку, а не крутит спиннер;
- [ ] по коду это `permission_denied` → `PermissionDeniedFailure`;
- [ ] повторное нажатие снова открывает диалог, согласие подключает.

### Дополнительно — то, что ломается чаще всего

- [ ] **двойной старт**: нажать «Подключиться» дважды подряд — второй раз ничего
      не происходит, второго туннеля нет (`already_running` Dart читает как успех);
- [ ] **стоп остановленного** — успех, не ошибка;
- [ ] **hot restart** при поднятом туннеле: `R` в `flutter run` — UI
      пересоздаётся и показывает `connected`, а не `idle` поверх живого туннеля;
- [ ] **смерть ядра**: `adb shell am force-stop` не подходит (убивает процесс
      целиком) — проверять на реальном падении; состояние обязано уехать в
      `error` с `core_crashed`, а не залипнуть в `connected`;
- [ ] **onRevoke**: поднять другой VPN-клиент — Commy сообщает причину, а не
      молча гаснет;
- [ ] **смена узла на лету** (`select`): открытые соединения выживают;
- [ ] **уведомление**: действие «Отключить» работает при закрытом приложении;
- [ ] **тайл**: подключение при закрытом приложении открывает его; отключение
      работает прямо из шторки, в том числе на заблокированном экране;
- [ ] **deep link**: `adb shell am start -a android.intent.action.VIEW -d "vless://…"`
      открывает приложение с заполненным импортом;
- [ ] **собственный трафик мимо туннеля**: `dev.commy.app` всегда в исключениях,
      иначе обновление подписки уходит в петлю;
- [ ] **always-on VPN + «блокировать без VPN»**: включить в системных настройках,
      перезагрузить телефон — сеть до первого запуска приложения не работает
      (это и есть отсутствие окна утечки из
      [чек-листа](../../../docs/09-security-privacy.md#чек-лист-утечек));
- [ ] **раздельное туннелирование**: приложение из списка исключений ходит мимо.

## Известные ограничения

- **Ядро живёт в том же процессе, что и UI.** Референсный клиент sing-box
  изолирует его в `:box`. Паника в Go у нас уносит и интерфейс. Возврат
  изоляции — это AIDL и вторая точка входа без Flutter; решение отложено, не
  забыто.
- **Автозапуск умеет только показать уведомление.** Причина — R2, см. KDoc в
  `BootReceiver.kt`. Пользователю, которому нужна гарантия отсутствия утечки при
  загрузке, нужен системный always-on VPN, а не эта галочка.
- **`readWIFIState()` всегда `null`** — правила по имени Wi-Fi сети не работают.
  Это цена за отсутствие разрешения на геолокацию.
- **`isConstrained` в `updateDefaultInterface` всегда `false`.** Несущая эту
  информацию capability есть только на очень свежих платформах, а угадать её
  неверно — значит заставить ядро душить себя на нормальном канале.
