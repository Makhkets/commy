# 18 · Эмулятор: живые проверки на слабой машине

> Как за десять минут поднять Android‑эмулятор, который не съедает машину,
> стенд с живыми узлами всех протоколов и панелью, и прогнать на них то, что
> юнит‑тесты не видят: переходы сети, сон, падение ядра, перезагрузку, kill
> switch. Написано в сессии 15 (2026-09-23) — всё ниже на этой машине
> выполнено, а не придумано.

---

## Зачем

Юнит‑ и виджет‑тесты (их 1400+) ни разу не поймали дефекты, которые нашлись
за первый же час на эмуляторе: уведомление «Подключено» после падения ядра,
кнопку «Проверить», которая проваливалась на рабочем туннеле, системное
«Назад», закрывавшее приложение, повтор интента «подключить» после ручного
отключения. Все они про стык приложения с Android — процесс, сервис,
уведомления, стек экранов, — а стык в тестах подменён фейками.

Эмулятор не заменяет телефон (другой GPU, другая скорость, сотовая сеть —
только имитация), но закрывает почти весь чек‑лист утечек и все критерии
приёмки M1, кроме «настоящего устройства».

---

## Машина владельца

Pentium G5400 (2 ядра / 4 потока), 32 ГБ, KVM есть, root нет, интернет
~120 КБ/с. Отсюда три правила:

1. **Экономить процессор, а не память.** Окно эмулятора, 1080p и программная
   отрисовка съедают ядра; RAM гостя почти ничего не стоит.
2. **Ничего не качать без нужды.** Образ Android — это час загрузки. Стенд
   работает на 127.0.0.1, трафик для замеров отдаёт локальный «blob».
3. **Не запускать тяжёлое параллельно.** Эмулятор + `flutter test` + сборка
   одновременно — это «System UI isn't responding» в госте.

| Что | Сколько на этой машине |
|---|---|
| Холодная загрузка `commy_lite` (API 36) | ~3 мин первый раз, ~40 с перезагрузка гостя |
| Холодная загрузка `commy_lite30` (API 30, ATD) | ~30 с |
| `flutter build apk --release --target-platform android-x64` | 1–4,5 мин (с тёплым кешем ~1 мин) |
| Весь `melos run test` | ~25 мин при запущенном эмуляторе |

## 1. Эмулятор

```bash
export ANDROID_HOME=~/Android/Sdk
scripts/emulator.sh create commy_lite "system-images;android-36;google_apis;x86_64"
scripts/emulator.sh start commy_lite      # headless, ждёт загрузку, выключает анимации
scripts/emulator.sh stop
```

Что делает `create`: AVD 720×1600 @ 280 dpi (тот же телефон шириной 411 dp,
что Pixel, но в 2,25 раза меньше пикселей), 2 ядра, 3 ГБ, без камер, звука и
GPS. `start`: `-no-window -gpu swiftshader_indirect -no-audio -no-boot-anim`.

**Какой образ.**

| Образ | Когда |
|---|---|
| `android-36;google_apis;x86_64` | Основной. Рутуется (`adb root`), в нём есть `tcpdump`, `iptables`, `su` — на этом держится чек‑лист утечек. Есть трансляция ARM, так что ставится и релизный APK под `arm64` |
| `android-30;aosp_atd;x86_64` | Второй уровень API (Android 11: ветка `registerNetworkCallback` без `BestMatching`, нет разрешения на уведомления). Самый лёгкий из существующих: **грузится за 30 с**, 103 пакета против 248, без Google‑сервисов. Рутуется, есть `tcpdump`. И главное — **в нём есть сотовая сеть** (LTE на `eth0` рядом с Wi‑Fi на `wlan0`): настоящий переход Wi‑Fi ↔ мобильная проверяется только здесь. Doze в нём выключен |

**Сборка под эмулятор** — релизная, но под x86_64 (быстрее трансляции и
ничем не отличается логикой):

```bash
cd apps/commy && fvm flutter build apk --release --target-platform android-x64
adb install -r build/app/outputs/flutter-apk/app-release.apk
```

Пакет — `dev.commy.app`, как у релиза. Debug‑сборка ставится как
`dev.commy.app.debug`: интенты и `am start` слать в тот пакет, который стоит.

## 2. Стенд: узлы и панель

```bash
XRAY_BIN=/usr/lib/nory/cores/xray/xray scripts/emulator_stand.sh start
scripts/emulator_stand.sh probe     # зонд в эмулятор
scripts/emulator_stand.sh links     # ссылки, если нужно импортировать по одной
scripts/emulator_stand.sh stop
```

Поднимается на 127.0.0.1 хоста — **в эмуляторе это 10.0.2.2**, из сети
машины не видно ничего:

| Что | Где |
|---|---|
| Xray: REALITY Vision / gRPC / XHTTP, TLS‑XHTTP h2, Trojan, SS 2022, VMess WS | 18443–18449 |
| Наше закреплённое ядро (`core/cmd/devbox`): Hysteria2, TUIC | 18450/udp, 18451/udp |
| Подписка как у Remnawave | `http://10.0.2.2:18080/sub/stand` |
| То же с лимитом устройств 1 | `http://10.0.2.2:18080/sub/hwid-stand` — без `x-hwid` отвечает заглушкой «App not supported», второму устройству — «Device limit reached» |
| «Blob» — цель для замеров | `http://203.0.113.10/blob?mb=N` **только через прокси**: узлы перенаправляют этот адрес на локальный сервер; запрос, ушедший мимо туннеля, не дойдёт никуда |

Узлы записаны **по имени** `10.0.2.2.nip.io` (публичный wildcard‑DNS), чтобы
резолвер адреса узла был на пути — ровно тот, из‑за которого до сессии 11
туннель ничего не возил.

Журналы: `$STAND_DIR/xray-access.log` (каждое соединение через узел с
назначением — доказательство, что трафик шёл через туннель), `core.log`
(Hysteria2/TUIC), `panel.log` (запросы подписки со всеми заголовками — видно
`x-hwid`, `x-device-os`, `x-ver-os`, `x-device-model`, User‑Agent).

## 3. Управлять приложением без рук

```bash
adb exec-out screencap -p > shot.png                   # снимок
adb shell input tap 360 540                            # тап по координатам
adb shell uiautomator dump /sdcard/ui.xml && adb pull /sdcard/ui.xml
```

Flutter отдаёт семантические метки в `uiautomator dump` (`content-desc`):
«Connect button», «Settings», «Refresh», «Check», имена серверов. Тап по
метке, а не по координатам, переживает прокрутку и смену раскладки — именно
вслепую по координатам в этой сессии трижды попадало не туда.

- Текст в поле: `adb shell input text "http://10.0.2.2:18080/sub/stand"`.
- **Esc (`keyevent 111`) закрывает лист целиком**, «Назад» (`keyevent 4`) при
  открытой клавиатуре — только клавиатуру.
- Ссылка из «чата»: `adb shell "am start -a android.intent.action.VIEW -d 'vless://…' dev.commy.app"`.
- Активный экран: `adb shell dumpsys activity activities | grep topResumedActivity`.
- Шторка: `adb shell cmd statusbar expand-notifications`; уведомления
  текстом: `adb shell dumpsys notification --noredact | grep -A40 pkg=dev.commy.app`.

## 4. Датчики

**Поднят ли VPN** (два очевидных способа врут, см. docs/17, сессия 10):

```bash
adb shell 'cat /sys/class/net/tun0/ifindex'            # номер = есть; тот же номер после перехода = не пересоздан
adb shell dumpsys vpn_management | grep 'Active vpn type'   # 1 поднят, -1 нет
```

**Идёт ли трафик и когда перестал:**

```bash
adb shell /data/local/tmp/probe get  'http://203.0.113.10/blob?mb=16'     # байты, время, скорость, SHA-256
adb shell /data/local/tmp/probe loop 'http://203.0.113.10/blob?mb=0' 250 60  # строка на запрос
curl -s 'http://127.0.0.1:18090/digest?mb=16'                              # эталонный SHA-256 на хосте
```

**Что ушло мимо туннеля** (нужен `adb root`):

```bash
adb shell "tcpdump -i any -y LINUX_SLL2 -n -s 160 -w /data/local/tmp/cap.pcap \
  'not (host 10.0.2.2 and portrange 18440-18451) and not net 127.0.0.0/8' &"
# … сценарий …
adb shell pkill -INT tcpdump && adb pull /data/local/tmp/cap.pcap
```

Всё, что ушло с `wlan0` не на 10.0.2.2/10.0.2.3, — кандидат в утечку.
`tcpdump` — истина о том, что покинуло устройство: пакет, отброшенный eBPF‑
фильтром Android, в нём не появится.

**Кто пытался** — счётчики по UID в цепочке перед `OUTPUT`:

```bash
iptables -N cleak; iptables -I OUTPUT 1 -o wlan0 -j cleak
iptables -A cleak -m owner --uid-owner 2000 -j RETURN     # «приложение» (shell)
iptables -A cleak -m owner --uid-owner 10216 -j RETURN    # сам Commy (узнать: pm list packages -U)
iptables -A cleak -m owner --uid-owner 1073 -j RETURN     # network_stack: пробы Android
iptables -L cleak -v -n -x
```

Счётчик в первой позиции видит и то, что потом отбросят, — поэтому выводы о
том, что **ушло**, только по `tcpdump`.

**Вести себя как приложение:** `adb shell su 2000 /data/local/tmp/probe …`.
Root системным kill switch не блокируется, uid 2000 — блокируется.
UID настоящих приложений (Chrome и т. п.) для этого плохи: у никогда не
открывавшегося приложения сеть закрыта своими ограничениями, и «таймаут»
будет про него, а не про туннель.

## 5. Сценарии (все прогнаны в сессии 15)

| Сценарий | Команды | Что должно быть |
|---|---|---|
| Смена сети | `probe loop …` в фоне; `svc wifi disable`; через 10 с `svc wifi enable` | `tun0` тот же номер, ни одного пакета приложений на `wlan0`, трафик идёт сам после появления сети. На API 30 Wi‑Fi уходит в LTE и обратно: теряется один запрос, бывший в полёте |
| Сон и Doze | `input keyevent 26; dumpsys battery unplug; dumpsys deviceidle force-idle`; потом `unforce; battery reset; input keyevent 224` | Ни одного провала в `probe loop` |
| Падение ядра | `kill -9 $(pidof dev.commy.app)` | VPN снят; уведомление **не** говорит «Подключено»; при открытии — «Ядро аварийно завершилось» |
| Kill switch | Настройки → Сеть → VPN → шестерёнка Commy → «Постоянный VPN» + «Блокировать соединения без VPN»; затем падение ядра | `su 2000 probe …` → `connect: permission denied` |
| Перезагрузка с автозапуском | «Запуск при загрузке» в Commy; `adb reboot` | Уведомление «Commy не подключён» сразу после загрузки; тап → приложение **подключается**; с kill switch до этого сеть закрыта |
| Отказ в VPN‑диалоге | Первое подключение → «Отмена» | Красная плашка «Туннель не может подняться без разрешения VPN» + «Разрешить» |
| Лимит устройств | Подписка `hwid-stand`, отправка HWID выключена | Карточка: «Панель прислала… App not supported» + «Включить и обновить» |

После `adb reboot` рут снимается: снова `adb root`, правила `iptables`
пропадают, зонд в `/data/local/tmp` остаётся.

## 6. Грабли эмулятора

- **В образе API 36 нет сотовой сети** (модем не регистрируется): там
  переход проверяется как «сеть пропала и появилась». Настоящий Wi‑Fi ↔ LTE —
  на образе API 30 `aosp_atd`.
- **Странное поведение одного протокола — прогнать тот же сценарий через
  другой.** REALITY после перехода сети молчал 75 с, и это выглядело как
  провал туннеля; Trojan через тот же стенд переключался чисто. Виновата была
  однопоточная приманка стенда (`openssl s_server`), теперь она
  многопоточная.
- **Лог ядра** в приложении — Диагностика → Логи. До сессии 15 в релизной
  сборке он был пуст (подписка открывалась до старта ядра); если он снова
  пуст — это регрессия, а не «ядро молчит».
- **Wi‑Fi образа API 36 идёт через `netsimd`**, а не через slirp самого
  эмулятора: `adb emu network capture` пишет пустой файл. Захват — `tcpdump`
  внутри гостя.
- **`ping` из‑под туннеля ничего не доказывает**: sing‑box отвечает на ICMP
  сам (0,3 мс). Для проверки — TCP (`probe`).
- **У toybox `nc` нет полузакрытия**: `printf … | nc host 80` завершается,
  не дождавшись ответа. Держать stdin открытым (`(printf …; sleep 5) | nc …`)
  или брать `probe`.
- **«System UI isn't responding»** сразу после загрузки на двух ядрах —
  это машина, а не приложение. «Подождать».
- Уведомление «Serial console enabled» — свойство образа эмулятора.
