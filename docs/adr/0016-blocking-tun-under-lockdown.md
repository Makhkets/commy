# ADR-0016 · Блокирующий TUN, пока туннель снят под системным kill switch

**Статус:** принято · 2026-09-24 агентом по поручению владельца («решения
принимай сам»; вопрос стоял в очереди как решение владельца, CLAUDE.md §7.4).
Откатывается только целиком, revert-ом коммита: блокировка вплетена в
жизненный цикл службы (`tearDownLocked`, `raiseBlockIfLockedDown`,
`holdBlock`/`watchLockdown`, `TunnelMarks`, `clearOrphan`), и удалить одну
функцию значит оставить интерфейс-чёрную дыру без уведомления.
**Контекст правил:** [R6](../../CLAUDE.md) — утечки трафика недопустимы;
[docs/09 · чек-лист утечек](../09-security-privacy.md#чек-лист-утечек).

---

## Проблема

Найдена на эмуляторе в сессии 16 (docs/09, «Прогон 2026-09-23, сессия 16»,
строка «Уточнение к kill switch включён»). При «Постоянный VPN» +
«Блокировать соединения без VPN» и **снятом** туннеле — пользователь нажал
«Отключить», старт не удался или ядро упало — соединения приложений
блокируются, как и обещано, а **DNS-запросы уходят в сеть открытым текстом**:
их шлёт netd от uid 0, а uid 0 Android выводит из-под блокировки
(`Vpn.java`, b/69873852). Провайдер видит каждое имя, которое открывают
приложения, — ровно у того пользователя, который включил самую строгую
защиту. Это поведение платформы (публично — Mullvad, 2024), но закрыть его
может только VPN-приложение: поднятый VPN забирает DNS устройства с собой.

---

## Решение

**Под системным kill switch служба не уходит, а держит «блокирующий» TUN:**
адрес, маршруты по умолчанию для IPv4 и IPv6, DNS внутри интерфейса, пустой
список нижележащих сетей и никого, кто читает дескриптор. Каждый пакет,
запросы имён тоже, остаётся в интерфейсе.

| Когда | Что происходит |
|---|---|
| «Отключить» (приложение, уведомление, плитка) | ядро снимается, на его месте — блокирующий TUN, уведомление «Не подключено · сеть закрыта» с «Подключить» и «Настройки VPN» |
| Ядро остановилось само, старт не удался | то же, приложение показывает ошибку; при остановке ядра — ещё и предупреждение в канале с обычной важностью |
| Always-on после загрузки или включения настройки | то же, плюс «Откройте приложение, чтобы подключиться» |
| Процесс умер, система перезапустила службу | блокирующий TUN возвращается; «Туннель остановился» и ошибка в приложении — только если туннель был поднят, а не одна блокировка |
| Процесс умер, перезапуска нет (Android 16), пользователь открыл приложение | `clearOrphan` просит службу вернуть блокировку |
| Подключение из блокирующего состояния | новый TUN ядра устанавливается **раньше**, чем закрывается блокирующий |
| Kill switch выключили в настройках | служба замечает за ≤ 5 с (опрос) и уходит, сеть возвращается, устаревшее предупреждение снимается |
| Другое VPN-приложение заняло слот | `onRevoke`: всё освобождается, ошибки не показывается |

**Как узнать, включён ли kill switch.** `VpnService.isLockdownEnabled()` и
`isAlwaysOn()` отвечают только приложению, чей VPN поднят **прямо сейчас**
(`getVpnIfOwner` в платформе; проверено дизассемблированием `services.jar`
образов API 30 и 36). После смерти процесса, до первого старта или из
always-on-запуска они говорят «нет» при любой настройке. Поэтому:

- с поднятым интерфейсом (ядра или блокирующим) — просто спрашиваем;
- без него — сначала поднимаем блокирующий TUN, потом спрашиваем, и при
  «нет» сразу закрываем. Делается это, только если есть причина: последний
  ответ платформы, сохранённый вне процесса (`TunnelMarks.lockdown`), или
  always-on-запуск — его доставляет только система и только always-on
  приложению. Пользователь без kill switch платит за это одним
  establish-и-закрытием при загрузке, если у него включён только «Постоянный
  VPN»;
- второй флаг (`TunnelMarks.tunnelUp`) отличает «туннель умер вместе с
  процессом» от «пользователь отключился, была только блокировка». Оба флага
  несекретные (R2).

**Все переходы — по одному.** Старт ядра, перезагрузка конфига, снятие,
подъём и снятие блокировки идут под одним `Mutex`. Без него «Отключить» во
время подключения, двойной тап или сбой ядра одновременно с «Отключить»
забирали дескриптор друг у друга: проигравший закрывал живой интерфейс или
оставлял себе уже сброшенный платформой, и VPN пропадал — ровно то окно, в
котором Android выпускает DNS.

Условие — `isAlwaysOn && isLockdownEnabled` (API 29+). **Без kill switch
«Отключить» не меняется:** сеть возвращается сразу. Одна правка задевает и
пользователей с одним «Постоянным VPN»: always-on-запуск, пришедший, пока
туннель поднимается или уже поднят, больше не гасит его (платформа шлёт его
повторно, `Vpn.java`: «if it's mid-setup onStartCommand will be sent twice»).

Порядок везде один: сначала `establish()` нового интерфейса, потом закрытие
старого. Окна «VPN нет совсем» не бывает — в таком окне Android и выпускает
DNS.

Своё приложение в блокирующий TUN не входит (`addDisallowedApplication`):
приложению-VPN система и так разрешает сеть под kill switch, и без этого не
работали бы обновление подписок и пинг до подключения.

**Цена, которую стоит знать.** Пока держится блокировка, VPN для системы
поднят: в строке состояния значок ключа, в системных настройках — «Подключено
/ Постоянно», а системное «Постоянный VPN отключён» не показывается.
Объяснение даёт наше уведомление; при сбое, а не по «Отключить», — ещё и
предупреждение в канале, который виден в строке состояния. И соединение
приложения больше не получает мгновенный `permission denied`: пакеты уходят в
интерфейс, который никто не читает, и приложение ждёт своего таймаута.

## Почему так, а не иначе

- **Ничего не делать («это платформа»).** Утечка настоящая, закрывается
  одним интерфейсом, а пользователь, включивший kill switch, уже выбрал «без
  VPN — никакой сети». Смысл «Отключить» для него не меняется: сеть была
  закрыта и остаётся закрытой; закрывается только то, что текло.
- **Держать блокирующий TUN всегда, без kill switch.** Меняет смысл
  «Отключить» для всех остальных: кнопка перестала бы возвращать сеть. Отвергнуто.
- **Отвечать на DNS `REFUSED` из маленького читателя пакетов.** Приложения
  падали бы быстрее, чем по таймауту, но это разбор IP/UDP в коде без
  юнит-тестов (у Kotlin-части их нет). Пустой список нижележащих сетей даёт
  почти то же дёшево: система отвечает приложениям «интернета нет», и
  большинство не ждёт таймаутов.
- **Наблюдать настройку, а не опрашивать.** `always_on_vpn_lockdown` —
  скрытая настройка, не часть публичного API, и платформа не обещает ни
  читать её, ни получать об изменениях уведомления. Публичный ответ —
  `VpnService.isLockdownEnabled()`, и его можно только спросить. Опрос — один
  вызов binder раз в 5 с, пока ничего другого не работает.

---

## Чего это не закрывает

- **Промежуток между смертью процесса и возвратом блокировки.** Ядро живёт в
  процессе приложения, дескриптор умирает вместе с ним; до перезапуска службы
  (а на Android 16 его может не быть вовсе) или до следующего открытия
  приложения имена текут, как и раньше.
- **Android 7–9.** `isLockdownEnabled` появился в API 29; ниже поведение
  прежнее.
- **Системные службы с `CONNECTIVITY_USE_RESTRICTED_NETWORKS`** (GMS) ходят
  мимо любого VPN — привилегия платформы.
