# ADR-0005 · Единый `CoreClient` и транспорты IPC

**Статус:** Accepted
**Дата:** 2026-08-01

## Контекст

Ядро sing-box живёт в разном месте на разных платформах, и это не наш выбор, а
требование ОС:

| Платформа | Где физически исполняется ядро |
|---|---|
| Android | В процессе приложения, внутри `VpnService` |
| iOS / macOS (стор) | В **отдельном процессе** — Network Extension |
| Windows | В **отдельном процессе** — служба с правами администратора |
| macOS (вне стора) | В **отдельном процессе** — привилегированный хелпер |
| Linux | В **отдельном процессе** — хелпер с `CAP_NET_ADMIN` |

То есть в четырёх случаях из пяти UI и ядро разделены границей процесса, часто ещё
и границей привилегий. Если позволить этой разнице протечь в код фич, приложение
превратится в пять приложений с общими виджетами.

## Решение

Один Dart-интерфейс **`CoreClient`** в пакете `commy_core`. Фичи знают только
его. Пять реализаций скрыты за фабрикой, выбирающей по `Platform`.

```dart
abstract interface class CoreClient {
  Future<void> start(CoreConfig config);
  Future<void> stop();
  Future<void> reload(CoreConfig config);

  Stream<TunnelStatus>    status;       // idle / starting / connected / stopping / error
  Stream<TrafficSample>   traffic;      // up/down bytes per second
  Stream<LogLine>         logs;
  Stream<List<Connection>> connections;

  Future<List<ProxyGroup>> proxies();
  Future<void>             select(String group, String tag);
  Future<Duration?>        urlTest(String tag, Uri probe);
}
```

Транспорт под интерфейсом:

| Реализация | Управление (start/stop) | Данные (статус, трафик, логи, прокси) |
|---|---|---|
| `AndroidCoreClient` | `MethodChannel` → Kotlin → `libbox` | `EventChannel` от `libbox.CommandServer` |
| `AppleCoreClient` | `MethodChannel` → Swift → `NETunnelProviderManager` | Unix-сокет в контейнере **App Group**, протокол `libbox.CommandClient` |
| `WindowsCoreClient` | Локальный TCP `127.0.0.1` + токен → служба | Тот же канал: Clash API (HTTP + WebSocket) |
| `MacosHelperCoreClient` | Unix-сокет в `/var/run` → хелпер | Clash API |
| `LinuxCoreClient` | Unix-сокет `/run/commy/ctl.sock` → хелпер | Clash API |

Два семейства протоколов вместо одного — сознательно:

- **Мобильные** используют `libbox.CommandClient`, потому что он уже написан,
  учитывает специфику расширений и не требует поднимать HTTP-сервер внутри
  процесса с лимитом памяти 50 MiB.
- **Десктопные** используют **Clash API** самого sing-box, потому что он тоже уже
  написан, даёт `/traffic`, `/logs`, `/connections`, `/proxies` и замер задержки —
  ровно то, что нам нужно, — и отлаживается обычным `curl`.

Своего протокола мы не изобретаем ни там, ни там.

Управляющий канал на десктопе **всегда авторизован**: служба генерирует токен при
старте и кладёт его в файл, читаемый только текущим пользователем. Без токена —
отказ. Слушаем строго на loopback.

## Альтернативы

**Свой единый gRPC/JSON-RPC поверх всего.** Красиво на бумаге. Отклонено: пришлось
бы тащить gRPC-рантайм в iOS-расширение с лимитом 50 MiB и заново реализовывать то,
что уже есть в `libbox` и Clash API.

**Прямой `dart:ffi` к ядру везде.** Работает только на Android (и то не идеально).
На iOS ядро обязано жить в расширении, на Windows/Linux — в привилегированном
процессе. FFI границу процесса не пересекает. Отклонено как физически невозможное.

**Разные интерфейсы для мобайла и десктопа.** Честнее отражает реальность, но
удваивает всю логику фич. Отклонено.

## Последствия

**Стало проще**
- Фичи и тесты пишутся против одного интерфейса. `FakeCoreClient` покрывает
  сценарии подключения без единого реального туннеля.
- Новая платформа = новая реализация `CoreClient`, ноль изменений в фичах.
- Отладка десктопа обычным HTTP-клиентом.

**Стало сложнее / за что платим**
- Пять реализаций надо тестировать раздельно; общий интеграционный набор тестов
  контракта обязателен (см. [10-testing.md](../10-testing.md)).
- Два протокола данных вместо одного — нужен слой нормализации в `commy_core`,
  приводящий и `libbox`-события, и Clash API к одним доменным типам.
- Токен и права доступа к управляющему сокету/порту — отдельная поверхность атаки.
  Разобрана в [09-security-privacy.md](../09-security-privacy.md).
