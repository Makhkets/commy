# 19 · Commy Cloud и Pro — отдельный продукт для операторов

> Статус: **клиентская часть Domain Recovery реализована** (сессия 24,
> [ADR-0019](adr/0019-subscription-domain-recovery.md), исключение E-4 в
> docs/09); сервер — каталог `cloud/`. Было: «роадмап, ничего не реализовано». Это не часть клиента 1.0 и не
> блокирует M0–M8. Зафиксировано решением владельца 2026-10-03: вводим
> платный необязательный сервис для людей, которые **держат свою VPN-панель**
> (Remnawave, Marzban, свой бэкенд) и раздают подписки через Commy своим
> клиентам — не для обычного пользователя, который просто вставил ссылку.

## 0. Как это соотносится с видением продукта

[00-vision.md](00-vision.md) держит список non-goals: «аккаунты, облачную
синхронизацию, бэкенд», «pro-версию» — и объясняет, почему: нечему утекать,
если ничего не собираем; опенсорс без подвоха. **Это решение не отменяется.**

Границу проводим так:

- **Базовый клиент Commy** (то, что ставит обычный человек) остаётся ровно
  таким, как описано в 00-vision и правиле R1 [09-security-privacy.md](09-security-privacy.md):
  ноль исходящих запросов, которых пользователь не запросил, три закрытых
  исключения. Ничего из этого документа ничего не меняет для него.
- **Commy Cloud** — отдельный продукт **для операторов**, которые сами решили
  подключить к своей подписке облачную функцию. Обычный пользователь, который
  импортировал ссылку от обычного Remnawave/Marzban без Cloud, никогда не
  видит ни одного байта трафика к Commy Cloud — приложение о нём не знает,
  пока подписка явно не помечена как облачная (см. §2.3).
- Там, где граница размывается — например, клиент фоном обращается к домену,
  который пользователь не вводил напрямую (подписка получена сама) — это
  **новое, четвёртое исключение из R1 (E-4)**, и оно описано явно, как E-1–E-3,
  а не тихо. Решение о нём принимает владелец проекта — см. §2.4 и §7.
- Код Commy Cloud (сервер, биллинг, дэшборд оператора) живёт **не в
  `commy_domain`/`commy_config`/`commy_core`** и не завязывает базовый клиент
  на свою доступность: если Commy Cloud пропадёт навсегда, обычная
  self-hosted подписка продолжает работать как ни в чём не бывало.

Если это соотношение неверно считано — стоп, спросить владельца, прежде чем
писать код по этому документу.

## 1. Контекст: зачем это Happ/INCY не предлагают

У Happ и INCY нет открытого кода, но тоже нет «облака для оператора» в этом
виде — максимум брендирование страницы подписки. Специфичная для операторов
Remnawave/Marzban боль, которую мы можем закрыть:

- Домен страницы подписки **банят или отбирают** (RU-реалии: Роскомнадзор,
  регистратор снёс домен, провайдер домена заблокировал аккаунт). У оператора
  сотни/тысячи уже выданных ссылок вида `оператор.ru/sub/<token>` — переписать
  их у всех клиентов руками невозможно.
- Нет единого способа посчитать, сколько людей реально живы на подписке, без
  эксплуатации собственного Remnawave API вручную.
- Нет способа мигрировать клиентов с одного поддоменного CDN на другой при
  DPI-блокировке конкретного домена, не трогая сам sing-box/Xray конфиг.

Это и есть ниша Commy Cloud: **инфраструктурная страховка для оператора**, не
функция для конечного пользователя.

## 2. Киллер-фича №1 — восстановление домена подписки (Domain Recovery)

### 2.1 Сценарий

1. Оператор заводит в Commy Cloud домен `makhkets.ru` и выпускает подписки
   вида `makhkets.ru/sub/<token>` — Cloud проксирует их на настоящую панель
   оператора (Remnawave/Marzban), сам не хранит конфиги узлов.
2. Домен `makhkets.ru` блокируют или отбирают.
3. Оператор заводит в Commy Cloud новый домен `makhkets.online`, подтверждает
   владение (TXT-запись/файл), нажимает «сделать основным».
4. При следующем плановом обновлении подписки (`SubscriptionScheduler`,
   M2 — уже умеет раз в минуту) клиент **у всех пользователей** обнаруживает,
   что подписка облачная, и подтягивает у Commy Cloud новый базовый домен —
   без переустановки, без новой ссылки, без действий пользователя кроме
   одного подтверждения в UI («провайдер подписки сменил адрес на
   `makhkets.online` — доверять?»).

### 2.2 Почему это не тривиально

- **Клиент не может просто довериться** ответу «вот твой новый домен» —
  это готовый вектор угона подписки (MITM на старом домене подменяет ответ и
  переводит всех клиентов на свой сервер). Ответ о смене домена должен быть
  **подписан ключом оператора**, который Cloud не видит и не хранит — аналог
  ключа подписи релиза ([ADR release-signing], по памяти владельца). Клиент
  проверяет подпись локально, Cloud — только courier.
- **Старый домен может быть мёртв**, когда апдейт случается — значит, канал
  проверки новой подписи не может быть «спросить у старого домена».
  Нужен стабильный адрес самого Commy Cloud (`api.commy.cloud` или похожий),
  который **не меняется** и которым подписаны все клиенты Cloud-подписок —
  см. E-4 ниже.
- **История смены домена** должна быть у оператора в дэшборде (аудит: кто,
  когда, с какого домена на какой), на случай спора с клиентом «меня
  перенаправили на фишинг».
- Нужен **аварийный тормоз**: если оператор сам скомпрометирован (украли
  доступ к дэшборду Cloud), угонщик не должен мгновенно перевести всех
  клиентов на свой сервер — минимум: смена домена видна в приложении как
  явное уведомление с возможностью отказаться и написать в поддержку
  оператора напрямую, не автоматический silent switch.

### 2.3 Как подписка узнаёт, что она облачная

Подписка, выпущенная через Commy Cloud, несёт поле-маркер (например,
`subscription-info`/заголовок ответа с полем `commy-cloud-id` и подписью).
Обычная самодельная Remnawave/Marzban-подписка без Cloud такого поля не
содержит и никогда не триггерит код Domain Recovery — ветка кода попросту не
исполняется, не «исполняется, но ничего не делает».

### 2.4 R1 — новое исключение E-4

| # | Что | Когда | Условие прозрачности |
|---|---|---|---|
| **E-4** | Проверка смены домена подписки у Commy Cloud (`api.commy.cloud` или итоговый домен) | Только для подписок с подписанным маркером Commy Cloud (§2.3), по тому же интервалу, что и обычное обновление подписки | Виден в UI как отдельный пункт «эта подписка использует Commy Cloud для восстановления домена»; сменa домена требует подтверждения пользователя, а не молчаливая |

Добавляется в таблицу исключений [09-security-privacy.md](09-security-privacy.md#тишина-в-сети--правило-r1-и-его-исключения)
**только одновременно с реализацией**, не раньше — пока это раздел роадмапа,
а не код.

### 2.5 Что сделано (сессия 24, 2026-10-05)

      точка встречи в обновлении подписки, вопрос «Перейти / Не доверять» на
      карточке, выключатель в меню подписки, строка в «Тишине в сети».
      Миграция БД v1 → v2 (`recovery_json`).
- [x] Сервер `cloud/` (Go): точки встречи `/r/{id}`, дэшборд с ключом и

      журнал, статистика визитов без хранения IP, доступность адресов, API с
      токенами, CLI `commy-cloud keygen/sign/verify`.

      подтверждает владение доменом — оператор сам добавляет заголовок
      (в Remnawave это одна настройка). Меньше доверия к Cloud, нет on-demand
      TLS для чужих доменов на общем Caddy. Прокси подписок — кандидат на v2.

## 4. Документация — «как у Happ»

У Happ и INCY аккуратный, приятный сайт документации — это то, чего у Commy
сейчас нет: есть только `docs/` для агента и разработчиков, на русском, без
вёрстки. Нужен отдельный публичный сайт на английском (+ ru), для конечного
пользователя и для операторов:

- Разделы: быстрый старт, импорт подписки (все схемы §3.1), маршрутизация и
  правила, устранение неполадок, FAQ, — отдельно — **Commy Cloud / Pro для
  операторов**: что это, как подключить домен, цены, API-референс.
  Pro-раздел — честно размеченный «необязательно», не затирающий факт, что
  база — опенсорс без доплаты.
- Технически: статический сайт (как у большинства клиентов-конкурентов) —
  решение по генератору (Docusaurus/Starlight/VitePress) принимается отдельно
  при старте работы, не в этом роадмапе.
- Авторство и тон — как в CLAUDE.md §5: UI-строки через `slang`, но
  сайт документации — отдельный репозиторий/каталог, не часть Flutter-кодогена.

## 5. Инфраструктура

**Развёрнуто 2026-10-05** (владелец разрешил): https://commy.makhkets.ru —
сайт, документация, дэшборд, точки встречи. Сервер `31.76.100.71`,
`/opt/commy-cloud` (docker compose, состояние — `data/cloud.json`,
`127.0.0.1:8097`), Caddy — контейнер `caddy-public`, конфиг
`/opt/caddy-public/Caddyfile` (явный блок `commy.makhkets.ru` и домен в `@infra`
шима on-demand TLS). DNS — Cloudflare, DNS-only. Админ дэшборда и пароль
сервера — в базе знаний владельца (записи 121 и 79). Обновление:
`cloud/deploy/deploy.sh`.

> Caddyfile примонтирован в контейнер **файлом**: `sed -i` создаёт новый inode,
> которого контейнер не видит. Править на месте (`cat > файл`) и проверять
> `caddy validate` перед `reload`. Чтобы снова связать файл хоста с
> контейнером, нужен `docker restart caddy-public` (секунды простоя всех сайтов
> сервера — делать в тихое время).

Исходный план раздела (до деплоя):

Владелец выделил сервер под `commy.makhkets.ru` (документация + Commy Cloud
backend рядом). **Ничего на сервер не разворачивалось в рамках этой сессии** —
только роадмап. Доступ к серверу (IP, логин) был передан в чате 2026-10-03;
хранить пароль в открытом виде в памяти агента не стал — по аналогии с тем,
как уже хранятся остальные секреты проекта (ключ подписи релиза — в GH
secrets + KB item 91 + `~/.config/commy-release`, не в тексте). Перед реальным
деплоем:

- [ ] Решить, что именно крутится на сервере первым: только статическая
      документация, или документация + Cloud backend сразу — задаёт
      требования к бэкапам и секретам на сервере иначе.
- [ ] Завести секреты сервера (пароль root, будущие ключи Cloud backend) в
      базе знаний владельца, как остальные — не в `docs/`, не в git.
- [ ] Это публикация/работа с секретами CI/инфраструктурой — пункт 5 из
      CLAUDE.md §7, обсуждается с владельцем явно перед первым деплоем, даже
      при общем решении «владелец делегирует §7» — доступ к серверу это
      бесповоротное действие (данные на живом сервере), не обычное решение
      по архитектуре.

## 6. Открытые вопросы владельцу

> Ответы 2026-10-05: деплой — да; код сервера — открыто в монорепо; Pro — пока
> бесплатно. Вопрос 1 смягчён архитектурой: точки встречи приходят из
> подписанного манифеста, их можно добавить или сменить без обновления

1. Домен для самого Commy Cloud API (устойчивый, не меняется) — отдельно от
   `commy.makhkets.ru`? Если его тоже заблокируют, вся Domain Recovery
   ломается рекурсивно — нужен план Б (несколько независимых anycast-доменов?
   IP напрямую как fallback?).
2. Чем Commy Cloud хостится — тот же сервер 31.76.100.71, или отдельная
   инфраструктура с резервированием, раз от его живости зависит
   восстановление доступа у реальных клиентов операторов?
3. Монетизация Pro — подписка за домен/месяц, за число активных клиентов,
   фиксированная плата? Это определяет форму API и биллинга.
4. Нужен ли ADR уже сейчас (до реализации), фиксирующий саму идею Commy Cloud
   как исключение из non-goals — или достаточно этого документа до момента,
   когда реализация реально начнётся?
